# YOLOCam

## A Rust-based RTSP camera monitor with FFmpeg decoding, automatic reconnection, live MJPEG dashboard, and YOLOv detection for people and cars at configurable intervals.


> Counts are per-frame detections, and totals are cumulative detection events.
> There is no object tracker, so the app does not count unique people or
> vehicles.

## Features

- RTSP H.264/H.265 input through an FFmpeg subprocess (TCP transport by default).
- Username/password support, including credentials embedded in a pasted RTSP URL.
- Automatic reconnects with exponential backoff and visible connection status.
- Start, Stop, and Reconnect controls.
- Local YOLO inference through the `ort` crate and ONNX Runtime.
- Only COCO class 0 (person) and class 2 (car) are reported.
- Letterbox preprocessing, RGB/NCHW normalization, raw YOLO output decoding,
  per-class NMS, and configurable confidence threshold (default `0.50`).
- Inference samples the newest frame only. If inference overruns the interval,
  stale frames are skipped instead of building a latency queue.
- Live MJPEG view with an HTML/SVG overlay for green person boxes and blue car
  boxes, confidence labels, camera FPS, AI time, and fullscreen.
- SQLite detection history with class and RFC 3339 time filters.
- Optional annotated JPEG screenshots: one file per analyzed frame, never one
  file per box, with timestamp, camera name, boxes, and confidence labels.
- Screenshot retention cleanup that only touches files generated by this app.
- WebSocket stats/detection updates, dark responsive dashboard, no frontend
  build step and no CDN dependencies.
- Graceful shutdown of FFmpeg, inference, HTTP streams, and SQLite.

## Architecture

```text
RTSP camera
    │  H.264 / H.265
    ▼
FFmpeg child process (TCP, 15s socket timeout, JPEG passthrough pipe)
    │  concatenated MJPEG frames
    ▼
MjpegParser ──► latest-frame watch slot (one frame, bounded memory)
                      │
                      ├──► browser MJPEG /api/stream (≤15 preview fps)
                      │
                      └──► once per interval (default 1000 ms)
                                 │
                                 ▼
                    JPEG decode → letterbox → YOLO ONNX
                                 │
                                 ▼
                    person/car filter → NMS → detections
                                 │
             ┌───────────────────┼────────────────────┐
             ▼                   ▼                    ▼
       annotated JPEG       SQLite events       WebSocket snapshot
       (one per frame)      (one per box)       + REST history
```

The decoding process, async HTTP server, inference thread, and database worker
are independent. Communication uses bounded channels and a latest-value watch
slot. The inference thread never blocks the RTSP reader.

## Quick start (Windows)

Tested on Windows 11 with Rust 1.100 (GNU toolchain), FFmpeg 9.1, ONNX Runtime
1.31.1, and YOLO11n FP32 ONNX.

1. **Install Rust** from <https://rustup.rs>. The project needs Rust **1.92+**
   because of `ort 2.0.0-rc.15`. For the default MSVC toolchain, install
   “Desktop development with C++” in Visual Studio Build Tools (SQLite is
   compiled from source by `rusqlite`). The GNU toolchain also works.
2. **Install FFmpeg 5.1+** and ensure `ffmpeg.exe` is on `PATH`:
   ```powershell
   winget install --id Gyan.FFmpeg -e
   ffmpeg -version
   ```
   Alternatively download a static build from <https://www.gyan.dev/ffmpeg/builds/>.
3. **Install ONNX Runtime 1.31.1** (CPU) into the project root:
   ```powershell
   powershell -ExecutionPolicy Bypass -File .\scripts\fetch-onnxruntime.ps1
   ```
4. **Get a model** (10.7 MB, SHA-256 checked by the script):
   ```powershell
   powershell -ExecutionPolicy Bypass -File .\scripts\fetch-model.ps1
   ```
   For production, export your own model as described below.
5. **Edit `config.toml`** and set `camera.rtsp_url`. Prefer environment variables
   for credentials.
6. **Build and run**:
   ```powershell
   cargo run --release -- --config config.toml
   ```
7. Open <http://127.0.0.1:8080>.

## YOLO model

### Option A: use the smoke-test model

`scripts/fetch-model.ps1` or `scripts/fetch-model.sh` downloads a community
YOLO11n COCO ONNX export (FP32, 640×640) and verifies its SHA-256:

```text
F7770B7229D2865585C9DEB639A93E6C1A1CAB3CF548A433261B2983486DF9DA
```

Place it at `models/yolo11n.onnx` (the default script destination). Model files
are ignored by git. Review the model/license terms before redistribution or
commercial use.

### Option B: export with Ultralytics (recommended)

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
source .venv/bin/activate
pip install ultralytics onnx onnxruntime

# YOLO11n, COCO, static 640 input, FP32
yolo export model=yolo11n.pt format=onnx imgsz=640 opset=12 \
  dynamic=False half=False simplify=True
```

YOLOv8n also works:

```bash
yolo export model=yolov8n.pt format=onnx imgsz=640 opset=12 \
  dynamic=False half=False simplify=True
```

Move the generated ONNX file to `models/yolo11n.onnx` and keep
`yolo.model_path` in sync.

**Expected model shape**

- Input: `float32[1, 3, 640, 640]` (NCHW, RGB, values 0–1).
- Raw output: `[1, 84, 8400]` or transposed `[1, 8400, 84]`.
  - 4 box values (`cx, cy, w, h`) + 80 COCO class scores.
  - Legacy YOLOv5-style 85-channel output (objectness + 80 classes) is also
    understood.
- Exports with embedded NMS/end-to-end output arrays, `float16` input, or a
  different number of COCO classes are rejected with a clear error.
- Dynamic input is accepted; if a spatial dimension is dynamic the app uses
  640×640. A static 640×640 export is recommended and is what the tests use.

The app intentionally reports only class 0 (`person`) and class 2 (`car`); all
other COCO classes are discarded after decoding.

## ONNX Runtime

`ort` is built with `load-dynamic`, so the app does **not** link ONNX Runtime at
build time. It loads the shared library at runtime.

- The `ort 2.0.0-rc.15` dependency targets **ONNX Runtime API 31 / 1.31.x**.
  The download scripts install **1.31.1**.
- Lookup order:
  1. `yolo.onnxruntime_path` in `config.toml`
  2. `ORT_DYLIB_PATH` environment variable
  3. `onnxruntime.dll` / `libonnxruntime.so` next to the executable
  4. the current working directory
  5. the OS loader's default search path
- `YOLOCAM_ONNXRUNTIME_PATH` is an additional environment override for
  `yolo.onnxruntime_path`.
- If you run `cargo run` from the project root, placing the library in the
  project root works.

Install CPU runtime:

```powershell
# Windows
powershell -ExecutionPolicy Bypass -File .\scripts\fetch-onnxruntime.ps1
```

```bash
# Linux / macOS
./scripts/fetch-onnxruntime.sh
```

### Optional GPU inference

CPU inference is the default and requires no GPU setup.

- **CUDA (Linux/Windows):**
  ```bash
  cargo build --release --features cuda
  ```
  Build/obtain an ONNX Runtime GPU distribution that contains the CUDA
  execution provider (`onnxruntime_providers_cuda.dll` on Windows), place it
  beside the ONNX Runtime library, install the matching CUDA/cuDNN runtime, and
  set:
  ```toml
  [yolo]
  device = "cuda"
  ```
- **DirectML (Windows only):**
  ```powershell
  cargo build --release --features directml
  ```
  Use an ONNX Runtime DirectML distribution with its provider libraries, then
  set `device = "directml"`.
- Provider registration is strict: if the requested execution provider cannot
  be registered, the model load reports an error instead of claiming GPU
  acceleration. The CPU scripts above install CPU-only binaries.
- GPU builds add build-time `ort` bindings but still load ONNX Runtime
  dynamically at runtime.

## FFmpeg

FFmpeg does all RTSP/transport/container/codec work. H.264 and H.265 are
supported directly by the FFmpeg build. The app runs:

```text
ffmpeg -hide_banner -loglevel warning -nostdin
  -rtsp_transport tcp -timeout 15000000
  -analyzeduration 5000000 -probesize 5000000
  -i <rtsp-url>
  -map 0:v:0 -an
  -vf "scale=w=min(1280,iw):h=min(1280,ih):force_original_aspect_ratio=decrease"
  -f mjpeg -q:v 5 -fps_mode passthrough pipe:1
```

- `-timeout` is in microseconds (15 seconds here).
- Decoded JPEG frames never exceed 1280×1280, which bounds preview encoding
  cost and bandwidth while leaving the YOLO input at 640×640.
- The raw RTSP URL is not logged; FFmpeg stderr is sanitized before display.
- Use FFmpeg **5.1 or newer** (`-fps_mode` is required). Tested with 9.1.

## Configuration

Copy and edit [`config.toml`](config.toml):

```toml
[camera]
name = "Front Camera"
rtsp_url = "rtsp://192.168.1.100:554/stream1"
# username = "camera-user"      # optional; prefer env vars
# password = "camera-password"  # optional; prefer env vars
reconnect_delay_seconds = 5
ffmpeg_path = "ffmpeg"

[yolo]
model_path = "models/yolo11n.onnx"
confidence_threshold = 0.50
interval_ms = 1000
detect_person = true
detect_car = true
device = "cpu"
# onnxruntime_path = "onnxruntime.dll"

[storage]
save_screenshots = true
screenshot_directory = "./detections"
retention_days = 7
database_path = "./yolocam.sqlite3"

[server]
host = "127.0.0.1"
port = 8080
```

| Key | Default | Notes |
| --- | --- | --- |
| `camera.name` | `Camera` | Dashboard label, DB camera name, filename prefix. |
| `camera.rtsp_url` | required | `rtsp://` or `rtsps://`. Credentials in the URL are extracted and stripped. |
| `camera.username` / `password` | none | Optional; prefer environment variables. |
| `camera.reconnect_delay_seconds` | `5` | Base backoff delay (capped at 60s, up to 5 doublings). |
| `camera.ffmpeg_path` | `ffmpeg` | Executable name or absolute path. |
| `yolo.model_path` | `models/yolo11n.onnx` | FP32 Ultralytics YOLO11/v8 COCO ONNX. |
| `yolo.confidence_threshold` | `0.50` | 0.0–1.0. Live-updatable. |
| `yolo.interval_ms` | `1000` | 100–60000 ms. Live-updatable. |
| `yolo.detect_person` / `detect_car` | `true` | At least one must be enabled. Live-updatable. |
| `yolo.device` | `cpu` | `cpu`, `cuda`, or `directml`; GPU requires a feature build. |
| `yolo.onnxruntime_path` | auto | Explicit runtime library path. |
| `storage.save_screenshots` | `true` | One annotated JPEG per analyzed frame with detections. |
| `storage.screenshot_directory` | `./detections` | Created on startup if possible. |
| `storage.retention_days` | `7` | 1–3650. Cleanup runs hourly and only deletes this app's timestamped `.jpg` files. |
| `storage.database_path` | `./yolocam.sqlite3` | SQLite file; WAL mode. |
| `server.host` / `port` | `127.0.0.1:8080` | Restart required after editing. |

Relative paths are resolved against the process working directory. Start the
app from the project root, or use absolute paths.

### Environment overrides

| Variable | Overrides |
| --- | --- |
| `YOLOCAM_CONFIG` | Config file path (default `config.toml`). |
| `YOLOCAM_RTSP_URL` | `camera.rtsp_url` (may contain credentials). |
| `YOLOCAM_RTSP_USERNAME` | `camera.username`. |
| `YOLOCAM_RTSP_PASSWORD` | `camera.password`. |
| `YOLOCAM_MODEL_PATH` | `yolo.model_path`. |
| `YOLOCAM_ONNXRUNTIME_PATH` | `yolo.onnxruntime_path`. |
| `ORT_DYLIB_PATH` | Runtime library fallback path. |
| `RUST_LOG` | Tracing filter, e.g. `yolocam=debug,ort=warn`. |

Environment camera credentials take precedence. While any RTSP URL or
credential override is active, the settings API marks the camera secret fields
as environment-managed and rejects changes to them. Environment credentials are
never persisted back to `config.toml`.

### Credentials and logs

- Startup logs print the **public** RTSP URL with userinfo removed.
- FFmpeg stderr is scanned for the effective URL, username, and password and
  replaced with `***` before logging or exposing an error message.
- `GET /api/settings` returns the URL without userinfo and only boolean
  `username_set` / `password_set` flags.
- The dashboard never receives the credentials.
- Credentials embedded in `config.toml` are stored on disk. Use environment
  variables when disk secrets are a concern, and restrict filesystem access.

### Security scope

The HTTP server is **unauthenticated** and binds to `127.0.0.1` by default. It
serves camera control endpoints and local admin configuration. If you bind to a
LAN address, put it behind authentication (VPN, authenticated reverse proxy, or
firewall rules). The app intentionally does not implement user accounts.

## Dashboard

- **Live view:** MJPEG, fullscreen button, camera FPS, last AI latency, current
  people/cars, boxes from the latest analyzed frame.
- **Statistics:** per-frame people/cars, cumulative person/car event totals,
  last detection timestamp, last analysis, camera FPS, inference time, full
  pipeline time, current interval.
- **Detection history:** class and from/to filters, timestamps in local time,
  confidence, camera name, screenshot link.
- **Settings:** RTSP URL, credentials, reconnect delay, FFmpeg path, model path,
  confidence, interval, enabled classes, device, runtime path, screenshot
  storage, retention. Model/device/runtime-path changes report that a restart is
  required; other changes apply live.

The green/blue boxes are DOM overlays positioned over the live MJPEG frame. They
show the newest completed analysis, so they can lag the live frame by up to one
detection interval. Saved screenshots have boxes baked into the JPEG.

## Detection events, screenshots, and retention

For each analyzed frame with at least one person/car:

- One annotated JPEG is written, not one per bounding box.
- Each detection becomes one SQLite row with timestamp, class, confidence,
  camera name, frame sequence, and screenshot filename.
- Totals increment by the number of boxes in that frame.
- If no person/car is present, the latest-frame/current counts become zero but
  cumulative totals and last-detection timestamp remain.

Filename format:

```text
<sanitized-camera-name>_YYYY-MM-DD_HH-MM-SS-mmm.jpg
# example: front-camera_2026-11-23_19-30-01-123.jpg
```

Screenshots are UTC-timestamped. Retention cleanup runs at startup and hourly;
it deletes only managed `.jpg` files older than `retention_days` in the
configured directory. SQLite history rows are retained, so a link to a removed
screenshot returns 404.

## API

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/api/health` | Liveness, camera status, AI state. |
| `GET` | `/api/stats` | Full dashboard snapshot. |
| `GET` | `/api/settings` | Safe settings (no credentials). |
| `POST`/`PUT` | `/api/settings` | Partial settings update; saves `config.toml`. |
| `GET` | `/api/history` | Detection rows. Query: `class=person\|car`, `from`, `to` (RFC 3339), `limit` (≤500), `offset`. |
| `GET` | `/api/frame.jpg` | Latest decoded JPEG, or 204. |
| `GET` | `/api/stream` | Multipart MJPEG (`multipart/x-mixed-replace`). |
| `GET` | `/api/screenshots/{filename}` | Stored annotated JPEG. Traversal-safe. |
| `POST` | `/api/camera/start` | Start or resume. |
| `POST` | `/api/camera/stop` | Stop FFmpeg, clear current frame/analysis. |
| `POST` | `/api/camera/reconnect` | Restart the capture worker. |
| `WS` | `/ws` | JSON snapshots: `{"type":"snapshot","data":{...}}`. |

Settings updates are partial. Omitted fields are unchanged. For credentials:
`null`/omitted keeps the current value, an empty string clears it, and
`clear_credentials: true` clears both. Replacing the camera host clears old
credentials unless new credentials are supplied. Some changes are applied
immediately (threshold, interval, enabled classes, screenshots); changes to
`model_path`, `device`, or `onnxruntime_path` return them in `restart_required`.

1. Confirm the stream plays outside the app:
   ```bash
   ffprobe -rtsp_transport tcp "rtsp://user:password@192.168.1.100:554/stream1"
   ```
   H.264 and H.265 are both fine.
2. Put the URL and credentials in `config.toml`, or:
   ```powershell

   cargo run --release -- --config config.toml
   ```
3. Watch the status pill change from Connecting to Live. Pull the network cable
   or restart the camera; the UI enters Reconnecting, and capture resumes with
   backoff.
4. Verify a saved screenshot under `detections/` and the history table.

### Local simulated RTSP with MediaMTX

1. Download [MediaMTX](https://github.com/bluenviron/mediamtx/releases) and
   start it (default RTSP port 8554).
2. Generate and publish a looping H.264 test video:
   ```bash
   ffmpeg -f lavfi -i "testsrc2=size=1280x720:rate=15" -t 12 \
     -c:v libx264 -g 15 -pix_fmt yuv420p test.mp4

   ffmpeg -re -stream_loop -1 -i test.mp4 \
     -c copy -f rtsp -rtsp_transport tcp rtsp://127.0.0.1:8554/cam
   ```
3. Point the app at `rtsp://127.0.0.1:8554/cam`.
4. Use a video containing people/cars for meaningful detections. The pattern
   source validates transport, decoding, reconnect, live view, and inference
   flow but will normally produce zero person/car detections.

H.265 transport test:

```bash
ffmpeg -re -stream_loop -1 -i test.mp4 \
  -c:v libx265 -x265-params keyint=15 -tag:v hvc1 \
  -f rtsp -rtsp_transport tcp rtsp://127.0.0.1:8554/cam265
```

MediaMTX authentication can also be enabled in `mediamtx.yml` to verify 401
handling and credential redaction.

## Troubleshooting

**`Unable to start FFmpeg (ffmpeg): ...`**
Install FFmpeg and confirm `ffmpeg -version` works from the same terminal. Set
an absolute `camera.ffmpeg_path` if PATH differs for the service/user.

**`Option not found` / unknown FFmpeg options**
Use FFmpeg 5.1 or newer. Older builds may not support `-fps_mode`.

**RTSP 401/404/timeouts**
Verify username/password and the exact stream path with `ffprobe`. H.265/H.264
are supported; an unsupported or non-existent path shows the FFmpeg error in
the UI and logs.

**`ONNX Runtime library not found` / load failure**
Run the fetch script or set `yolo.onnxruntime_path` / `ORT_DYLIB_PATH`. The
`ort 2.0.0-rc.15` build expects an API-31 (1.31.x) runtime. A mismatched major
version fails at load time.

**`model input ... uses float16`**
Export with `half=False`. FP32 input is supported; FP16 input is deliberately
rejected with this message.

**`unsupported YOLO output format`**
Use a raw Ultralytics detection export with no NMS/end-to-end graph. Expected
84-channel COCO output (`[1,84,8400]` or transposed) or legacy 85-channel output.

**`model file not found`**
Paths are relative to the process working directory. Run from the project root
or use an absolute path.

**GPU requested but unavailable**
The app reports the provider registration/load error. Install a matching ONNX
Runtime GPU/DirectML distribution and the vendor runtime, or switch
`device = "cpu"`.

**Database is busy**
Only one YOLOCam instance should use a given SQLite file; WAL mode and a busy
timeout are set. Check filesystem permissions.

**Screenshots are not written**
Confirm `save_screenshots = true`, the process can create/write the screenshot
directory, and at least one person/car exceeds the confidence threshold. Warnings
are rate-limited to avoid log spam.

**Dashboard unreachable or streams stall behind a proxy**
Check the bind address/port. A reverse proxy must forward WebSocket traffic to
`/ws` and disable response buffering for `/api/stream` (the app sends
`X-Accel-Buffering: no`).

**Low frame rate / high CPU**
MJPEG encoding is CPU-intensive. The preview is capped to 1280×1280 but live
conversion still costs CPU. Lower camera resolution/FPS, use a stronger CPU, or
change the preview quality/filter in `src/rtsp.rs` after benchmarking.

## Design notes and limitations

- No object tracking: “People now” and “Cars now” are detections in the newest
  analyzed frame; totals are detection events, not unique entities.
- AI runs once per interval, not per video frame. Live frames continue between
  analyses.
- The browser receives MJPEG, not the original H.264. The stream is throttled to
  at most 15 preview fps to limit CPU/bandwidth; the displayed camera FPS is the
  decoded preview rate. No audio.
- Bounding boxes in the browser are aligned to the latest analysis; saved
  screenshots are fully annotated server-side.
- Inference can overrun the interval. The scheduler then analyzes the newest
  available frame immediately and does not queue stale frames; CPU can saturate
  if inference is persistently slower than the configured interval.
- A single ONNX session/thread is used. ONNX Runtime may use up to four intra-op
  threads by default for CPU inference.
- Detection rows are retained indefinitely; only screenshot files are cleaned
  up. Links to expired screenshots return 404.
- The settings API is local-admin functionality and has no authentication.
- RTSP decoding is handled by a supervised FFmpeg process. If FFmpeg is missing
  or the stream fails, the dashboard stays available and reports the error.
